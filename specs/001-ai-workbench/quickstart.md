> Feature: [AI 工作台](./spec.md) | Plan: [plan.md](./plan.md) | 契约: [contracts/api.md](./contracts/api.md) · [contracts/dsl.md](./contracts/dsl.md)

## 1. 前置条件

| 项 | 要求 | 怎么确认 |
|---|---|---|
| 后端依赖 | `backend/.venv` 已装齐 `requirements.txt`（**含新增的 `pypdf`、`python-docx`**） | `cd backend && .venv/bin/python -c "import pypdf, docx"` |
| 数据库 | MySQL 可连；启动时自动建表（含 4 张新表） | 见 §2.1 |
| Redis | 可选（`REDIS_ON`）；关闭时定时任务可能重复执行 | `conf/dev.env` |
| AI 厂商 | **至少一个厂商已启用且配置了 API Key**，至少一个 `chat` 模型已启用 | 后台「模型设置」页 |
| 被测接口 | 至少一个可访问的 HTTP 接口（用于验证采纳后的用例能真跑） | 自备 |

## 2. 启动与准备

### 2.1 起后端

```bash
cd backend
source .venv/bin/activate
python pity.py            # 或 uvicorn main:pity --reload
```

启动日志应出现 4 张新表的建表信息：

```
pity_ai_draft_batch
pity_ai_case_draft
pity_ai_invoke_log
pity_ai_analysis
```

### 2.2 起前端

```bash
cd frontend
nvm use                   # 必须 Node 20（见 frontend/CLAUDE.md）
npm install --ignore-scripts
npm run start:dev         # localhost:8000
```

### 2.3 准备一个项目与目录

UI 用例与 API 用例共用既有的项目与目录树。本功能**不新建**项目/目录概念 —— 直接复用既有的：

- 建一个项目
- 在项目下建一个目录（如 `登录模块`）—— 记下它的 id，后续用作"采纳目标目录"

## 3. 端到端验证场景

### 3.1 场景 A：需求文本 → 用例草稿 → 采纳 → 用例可执行

**这是最核心的一条，串起了 FR-002 / FR-005 ~ FR-012。**

**步骤**：

1. 登录 → 进入 `/ai/casegen`
2. 左侧表单：选项目 → 选目标目录 → 填任务标题 → 测试类型选 **API 用例** → 选模型
3. 在「文本输入」里粘贴一段需求，例如：

   ```
   用户登录接口 POST /api/login，参数 mobile(手机号) 与 code(短信验证码)。
   验证码错误时返回 code=10001 msg="验证码错误"；
   成功时返回 code=0 与 data.token。
   手机号为空返回 code=10002。
   ```

4. 点「开始生成用例」
5. **预期**：右侧出现草稿表，每行有标题、编码、优先级、类别、状态、步骤数

**校验点**：

| 检查 | 期望 |
|---|---|
| 草稿条数 | ≥ 3（正常路径 + 验证码错误 + 手机号为空） |
| 每条的 `warn` | 无 `out_parameters` 缺失的告警（正常生成时应自带出参声明） |
| 打开某条详情 | 断言的 `actually` 用 `${变量}` 引用，且该变量在 `out_parameters` 中存在 |

6. 勾选 2–3 条 → 点「批量采纳」
7. **预期**：提示"采纳完成：成功 N 条"；草稿状态变「已采纳」
8. 回到接口用例列表 → 打开目标目录
9. **预期**：新出现的用例带上了前置/后置步骤与断言；**用例状态是「调试中」不是「正常运行」**
10. 选中其中一条 → 执行
11. **预期**：能真的跑通并产生结果（这验证了 DSL → 四张表的映射没有错）

**幂等验证**：回到草稿表，对同一批草稿再点一次「批量采纳」
- **预期**：提示跳过（`case_id` 已回填），**用例数量不增加**

### 3.2 场景 B：文档 → 草稿

**FR-003。**

1. 在「文档上传」里选一个 `.docx`（或 `.pdf` / `.md` / `.txt`）
2. **预期**：解析出正文并显示字数
3. 点「开始生成用例」→ **预期**：草稿表出现内容与该文档相关的用例
4. 上传一个 `.exe` 之类的非法类型
   - **预期**：明确提示"不支持的文件类型, 当前支持 PDF / Word / Markdown / 纯文本"，**不静默失败**
5. 上传一个空的 `.txt`
   - **预期**：提示未解析到内容，并建议改用文本输入

### 3.3 场景 C：失败用例 → 根因分析

**FR-016 ~ FR-022。**

1. 造一个会失败的用例（如断言一个不可能成立的值）并执行，产出报告
2. 在报告详情页选中这条失败用例 → 点「AI 分析」
3. **预期**：
   - 无需再提供任何材料即出结论
   - 每条根因假设都带 `evidence`，且 evidence 是执行上下文里的**原文**（如响应体里的那行 JSON）
   - 有「如何自证」的清单
   - 有修复建议与复现步骤
4. 点「用此生成用例」
   - **预期**：跳到 `/ai/casegen`，需求输入框已预填复现步骤

**粘贴模式**：另开 `/ai/bug`，粘贴一段 `Traceback` → **预期**：输出结构与上面一致。

### 3.4 场景 D：日志 → 错误簇 → 归因

**FR-023 ~ FR-026。**

1. 打开 `/ai/log`，粘贴一段含重复异常的日志（同一异常重复 20 次 + 另一类异常 3 次）
2. **预期**：
   - 聚成 **2 个簇**（不是 23 个）
   - 每簇有次数、首次/末次出现时间、样例
   - 两次出现间隔明显的一段被标为「异常突增」
3. 对第一个簇点「分析」
   - **预期**：根因解释引用了簇内的具体日志行

**平台自身日志**：用无权限账号访问 → **预期**：拒绝，提示无权访问平台运行日志。

### 3.5 场景 E：SQL 慢查询 → 改写 → 验证

**FR-027 ~ FR-031。**

1. 在 `/ai/sql` 打开慢查询排行
   - **预期**：按耗时倒序，列出 SQL、所属库、执行者
2. 选一条点「分析」
   - **预期**：给出执行计划、问题点、索引建议、改写后的 SQL
3. 点「执行验证」（走既有 `POST /online/sql`）
   - **预期**：跑出结果与耗时，可与原耗时对比
4. **只读验证**：找一条 `UPDATE` 语句做分析
   - **预期**：只返回执行计划，**目标 SQL 没有被执行**

## 4. 就地指引点验证（constitution 原则 IV）

**这五条是 constitution 原则 IV 的落地验收，必须逐条走一遍。** 每条都是"把前置条件拿掉，看界面是否在原地给出指引"。

> **G1–G5 的唯一定义在 [`data-model.md` §5](./data-model.md#5-就地指引点constitution-原则-iv)**，本节只做验证，不重复定义 —— 避免两处漂移。

| 编号 | 操作 | 期望 |
|---|---|---|
| **G1** | 把所有厂商停用（或用未配 API Key 的厂商）→ 进入 `/ai/casegen` | 顶部出现提示条说明当前无可用模型并给出跳转「模型设置」的入口；「开始生成」按钮不可用 |
| **G2** | 选一个没有子目录的项目 → 打开目标目录选择器 | 旁边有「新建目录」入口，就地建完即选中；不是只报"请先选择" |
| **G3** | 取消对象存储配置 → 上传文档 | 提示"未配置对象存储, 文档将仅本次解析不落盘"并给出配置入口；**上传仍能继续** |
| **G4** | 在一个没有元素的新项目下 → 测试类型选「Web UI 用例」 | 表单内提示需要先沉淀元素，并给出跳转元素库的入口 |
| **G5** | 把厂商 API Key 改错 → 发起生成 | 结果区显示可操作原因（哪个厂商、HTTP 状态、建议动作），并有「重试」按钮；草稿表保持原样，不产生半成品批次 |

> G1 与 G5 的区别：G1 是**事前可知**（配置缺失，提交前就能拦），G5 是**事后可知**（调用本身失败）。两者都必须给指引，不能只报错误码。

## 5. 回归脚本

constitution 原则 V：**落地前 MUST 通过自动化验证**。

```bash
cd backend
.venv/bin/python scripts/ai_workbench_selftest.py    # 内核级, 不需要起后端
.venv/bin/python scripts/ai_workbench_e2e.py         # 端到端, 默认连 127.0.0.1:7777
```

| 脚本 | 覆盖 |
|---|---|
| `selftest` | JSON 提取（markdown 包裹 / 前后废话 / 括号嵌套 / 字符串内含括号）；**14 条校验规则每条的正反例**（尤其规则 8：断言引用未定义变量必须报错；规则 13：Web UI 步骤引用不存在的元素必须被丢弃并告警）；提示词注入样本（文档里写"忽略前面的指令"必须被当作数据）；日志归一化与指纹聚类；`EXPLAIN ANALYZE` 拦截 |
| `e2e` | 草稿批次与草稿的 CRUD；生成 → 审核 → 采纳 → 用例入库 → 用例可执行；采纳幂等（重复采纳不产生重复用例）；驳回；三类分析结论入库且不覆盖；权限（平台日志需 admin） |

前端验收：

```bash
cd frontend
nvm use
npx tsc --noEmit          # 目标 0 错误
npm run lint:js
```

## 6. 验收标准对照

### 6.1 可自动验证的标准

| 成功标准 | 怎么验 |
|---|---|
| SC-003 采纳后无"断言取值取不到值"的用例 | 场景 A 步骤 11：所有采纳的用例逐条执行，断言必须真能取到值 |
| SC-006 错误簇数比逐行处理降一个数量级 | 场景 D：23 行日志 → 2 个簇 |
| SC-009 平台日志对无权限用户不可用 | 场景 D 的权限验证 |
| SC-010 100% 可执行产物经人工审核才落地 | 场景 A：生成后、采纳前，用例库里查不到任何新用例 |

### 6.2 需人工判定的标准（含抽样口径）

SC-002、SC-004、SC-007、SC-008 判定的是 **AI 产出的质量**，本质需要人判断"方向对不对"。为让它可复现、可对比，约定抽样口径：

| 项 | 约定 |
|---|---|
| **抽样规模** | 每个场景至少抽取 **10 个样本**；样本不足 10 个时全量判定，并在结论里注明样本量 |
| **抽样来源** | 取最近 3 次生成/分析任务的结果，各随机抽取若干条；**不得挑选表现好的样本** |
| **判定人** | 至少 2 人独立判定；不一致的样本由第三人裁定 |
| **判定口径** | 只判"方向是否正确"，不判"表述是否完美"；边界样本一律计为"不正确"（保守） |
| **判定记录** | 录入 `backend/scripts/ai_workbench_eval.py` 的 JSONL 记录文件，字段：场景、样本 id、判定人、结论（正确/不正确）、备注 |
| **用途** | 记录留存用于后续按模型聚合对比（对应 FR-015 的"效果比对"），**不用于自动打分阻断流程** |

> **为什么不用自动化判定**：constitution 原则 V 要求"MUST NOT 只靠手动点一遍"，但"AI 结论方向是否正确"没有可靠的自动判据。折中是**把人工判定固化成有口径、可复现、可对比的记录**，而不是假装它能自动测。

| 成功标准 | 怎么验 |
|---|---|
| SC-001 上传文档到看到草稿 ≤ 5 分钟 | 场景 B 计时，3 次取中位数 |
| SC-002 ≥ 60% 草稿可不改请求内容直接采纳 | 场景 A 统计：采纳成功条数 ÷ 总条数，按 §6.2 口径抽样 |
| SC-004 ≥ 80% 根因假设带原文依据 | 场景 C 统计有 `evidence` 的假设占比（**此项可自动统计**，人工只做抽样核对） |
| SC-005 相比人工翻日志耗时降 50% | 场景 C 计时对比（人工读执行日志 vs 点一次分析），各 3 次取中位数 |
| SC-007 ≥ 70% 簇归因被判定方向正确 | 场景 D 按 §6.2 口径抽样判定 |
| SC-008 改写 SQL 可用率 ≥ 60% | 场景 E 批量统计 |

## 7. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 点「开始生成」没反应 | 无可用模型（G1） | 按 G1 指引配置 |
| 草稿出来了但全带告警 | 模型没产出 `out_parameters` | 看告警内容；必要时人工补（草稿详情可编辑） |
| 采纳报"目标目录不存在" | 目录被删了 | 换目录重新生成批次 |
| 慢查询排行是空的 | 还没在 `/online/sql` 执行过 SQL | 先去 SQL 客户端跑几条 |
| 分析结论没有 `evidence` | 上下文里确实没有可引用的原文（如只有堆栈没有响应） | 属正常降级；前端会标灰提示低可信 |
