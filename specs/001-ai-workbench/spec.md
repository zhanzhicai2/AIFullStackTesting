# Feature Specification: AI 工作台

**Feature Branch**: `001-ai-workbench`

**Created**: 2026-10-26

**Status**: Draft

**Input**: User description: "为 Pity API 测试平台新增四个 AI 辅助场景（用例生成 / Bug 分析 / 日志分析 / SQL 分析），统一挂在一个 AI 菜单下。用例生成提供左侧需求输入 + 右侧草稿审核的生成工作台；AI 产出的可执行产物先进草稿态，人工审核后才落地。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 从需求文档生成用例草稿并审核采纳 (Priority: P1)

测试人员拿到一份新的需求说明（产品文档、Word/PDF/Markdown/TXT），希望在平台上快速得到一批可执行的接口测试用例，而不是从零手写。

测试人员进入「用例生成工作台」，选择所属项目和采纳目标目录，填写任务标题，选择测试类型与本次使用的模型，然后上传需求文档（或直接粘贴需求文本），点击「开始生成用例」。工作台右侧出现一批**用例草稿**，每条列出标题、编码、优先级、类别、状态和步骤数。

测试人员逐条或批量查看草稿内容，把不合适的驳回、把合适的采纳。被采纳的用例进入目标目录下的正式用例库，并自动带上前置/后置步骤与断言；草稿被采纳后仍可从生成记录里追溯。

**Why this priority**: 这是整个功能的门面与主要价值来源。其他三个分析场景都建立在"平台已有执行数据"之上，而用例生成是唯一能把平台外的新需求带进来的入口。少了它，AI 工作台只是一个只读的分析看板。

**Independent Test**: 用一份真实需求文档走完"上传 → 生成 → 审核 → 采纳 → 在正式用例库里看到用例"这条完整路径，即可独立验证该故事交付了价值。

**Acceptance Scenarios**:

1. **Given** 用户已选定项目与采纳目标目录，**When** 上传一份需求文档并点击「开始生成用例」，**Then** 工作台右侧出现该任务的用例草稿列表，每条含标题、编码、优先级、类别、状态与步骤数
2. **Given** 草稿列表已展示，**When** 用户勾选若干条并点击「批量采纳」，**Then** 这些用例出现在所选目标目录的正式用例库中，且草稿状态变为已采纳；同一条草稿被重复采纳不会产生重复用例
3. **Given** 草稿列表已展示，**When** 用户勾选若干条并点击「批量驳回」，**Then** 这些草稿状态变为已驳回且不写入正式用例库
4. **Given** 一次生成任务已完成，**When** 用户按状态筛选草稿列表，**Then** 列表只显示该状态的草稿，且数量与状态计数一致
5. **Given** 用户尚未选择目标目录或未选择模型，**When** 用户查看生成工作台，**Then** 界面在对应位置就地说明该去哪里配置或选择，而不是只提示"请先选择"后让用户无从下手
6. **Given** 一批草稿中混有内容不合规的条目，**When** 用户查看草稿详情，**Then** 不合规的字段被标出，且用户可单独修正该条草稿并保存，保存后仍可被采纳，而不是整批作废
7. **Given** 用户上传的文件格式不受支持或文件损坏，**When** 平台解析该文件，**Then** 明确告知解析失败原因并让用户改用文本输入，而不是静默产出空草稿
8. **Given** 测试类型选择 Web UI 用例，**When** 生成的草稿中有步骤引用了元素库中不存在的元素，**Then** 该步骤被标出且该草稿在采纳前被拦下，不写入正式用例库
9. **Given** 测试类型选择 Web UI 用例，**When** 用户在元素库为空的项目下打开生成工作台，**Then** 界面就地说明需要先沉淀元素并给出前往元素库的入口

### User Story 2 - 对失败用例做根因分析 (Priority: P2)

测试人员跑完一轮回归，报告里有几条用例红了。他想快速知道**为什么红**，以及**怎么改**，而不是自己去翻日志、猜代码。

测试人员在测试报告详情页选中失败的用例，点击「AI 分析」。平台自动取来这一次执行的请求内容、响应内容、断言失败明细、执行日志、耗时与重试次数，并附带该用例最近若干次的执行历史。平台给出按可信度排序的根因假设，每条假设都引用分析材料里的原文作为依据，并附带一张"如何自证这个判断"的清单和修复建议；最后给出一份可复现步骤。

测试人员如果手头只有一段报错堆栈，也可以直接粘贴进去分析。

**Why this priority**: 失败分析是 AI 在测试平台上准确率最高的场景——上下文是结构化的、完整的、平台自己跑出来的，不需要用户手工喂料。它把"报告里一个红色的 X"变成"一条可执行的修复建议"，节省的是排查时间而不是录入时间。

**Independent Test**: 在一份含失败用例的真实报告上触发分析，并单独用一段粘贴的堆栈文本走一遍，即可独立验证该故事。

**Acceptance Scenarios**:

1. **Given** 测试报告中有一条失败用例，**When** 用户在该用例上点击「AI 分析」，**Then** 平台无需用户再提供任何材料即给出根因假设、依据、修复建议与复现步骤
2. **Given** 分析已返回结论，**When** 用户查看每条根因假设，**Then** 该假设列出了它所依据的原文片段；没有依据引用的结论被明确标记为低可信
3. **Given** 某条用例在历史上多次失败且失败表现一致，**When** 用户查看分析结果，**Then** 结果中明确给出该失败是「必现」还是「偶发」的判定，并列出判定所依据的历史执行摘要
4. **Given** 某条用例是首次执行、没有任何历史可比，**When** 用户查看分析结果，**Then** 结果明确说明缺少历史对比数据，不臆造历史规律
5. **Given** 用户只有一段报错堆栈文本，**When** 用户粘贴并发起分析，**Then** 平台给出与上述结构一致的结论
6. **Given** 分析结论中的复现步骤，**When** 用户选择据此生成用例，**Then** 平台把复现步骤带入用例生成工作台并预填需求输入，用户无需重新描述
7. **Given** 模型调用失败或返回内容无法解析，**When** 用户查看结果，**Then** 平台给出可操作的失败原因，而不是空白或原始乱码

### User Story 3 - 日志错误聚类与归因 (Priority: P3)

开发或运维拿到一大段日志，想知道**主要错误是哪几类**、**什么时候开始集中爆发**，而不是逐行读。

用户把日志交给平台（平台自身日志、已上传的日志文件，或直接粘贴文本）。平台先把日志里的异常按"错误长什么样"归并成若干**错误簇**，给出每簇出现次数、首次与末次出现时间、涉及范围，并标出异常突然增多的时间段；然后对排名靠前的错误簇逐个给出根因解释。

**Why this priority**: 日志量级往往远超人工阅读能力，聚类是这个场景的核心价值。但它服务的是排查者而不是造用例的人，落地顺序排在用例生成与失败分析之后。

**Independent Test**: 拿一份含重复异常、且含错误突增时段的真实日志走完"输入 → 聚类 → 逐簇归因"这条路径即可独立验证。

**Acceptance Scenarios**:

1. **Given** 用户提交一份日志，**When** 平台完成处理，**Then** 返回错误簇列表，每簇包含出现次数、首次与末次出现时间、涉及范围，以及该簇的错误样例
2. **Given** 日志中存在同一错误的大量重复与若干不同错误，**When** 用户查看聚类结果，**Then** 相同错误被归为同一簇而不同错误分属不同簇
3. **Given** 日志中某个时间段的错误数量显著高于其他时段，**When** 用户查看聚类结果，**Then** 该时段被明确标记为异常突增
4. **Given** 错误簇已生成，**When** 用户对排名靠前的错误簇发起归因，**Then** 每个簇得到根因解释，且解释引用该簇中的具体日志行
5. **Given** 用户提交的是平台自身的运行日志，**When** 无权限的用户尝试访问，**Then** 访问被拒绝；平台自身日志的分析能力不对不具备该权限的用户开放

### User Story 4 - SQL 慢查询排行与改写建议 (Priority: P4)

开发人员想知道**哪些 SQL 慢**、**为什么慢**、**怎么改快**，并且希望**改完能验证**。

平台对已记录的历史 SQL 执行按耗时排行；对其中任意一条，平台采集它的执行计划、涉及表的结构与索引信息，给出问题点、索引建议与改写后的 SQL。用户可以把改写后的 SQL 直接在平台里执行一遍，对比耗时。

**Why this priority**: 数据源已经现成、不产生任何副作用，是四个场景里风险与成本最低的。排在最后是因为它服务的是开发人员而非测试人员，受众更窄。

**Independent Test**: 在一条已知较慢的 SQL 上走完"排行 → 分析 → 一键执行改写后 SQL 对比耗时"这条路径即可独立验证。

**Acceptance Scenarios**:

1. **Given** 平台已记录若干条 SQL 及其耗时，**When** 用户打开慢查询排行，**Then** 按耗时从高到低列出，并显示每条 SQL 所属的库与执行者
2. **Given** 用户对某条 SQL 发起分析，**When** 分析完成，**Then** 平台给出问题点、索引建议与改写后的 SQL，且这些结论引用了该 SQL 的执行计划与表结构信息
3. **Given** 平台给出了改写后的 SQL，**When** 用户点击执行，**Then** 平台在既有 SQL 执行入口中运行它并展示结果与耗时，供用户对比
4. **Given** 用户提交的 SQL 会修改数据，**When** 平台采集其执行计划，**Then** 平台只做不改变数据的计划采集，绝不因为采集计划而执行该 SQL
5. **Given** SQL 分析请求包含一段外部文本，**When** 平台把它作为分析材料处理，**Then** 该文本只被当作待分析的数据，不会被当成指令执行

---

### Edge Cases

- **生成的内容不合规**：模型产出的用例中若含平台不支持的断言方式、优先级或步骤类型，对应内容被标出并可单独修正；一条草稿的个别字段出错不得导致整批草稿作废
- **断言引用了不存在的响应字段**：若生成的断言取值取不到值，该草稿必须在采纳前被拦下，而不是采纳后静默失败
- **Web UI 用例引用了不存在的元素**：若某步骤引用的元素在元素库中不存在或已停用，该步骤被标出，该草稿必须在采纳前被拦下，不得写入用例库
- **模型不可用**：厂商未启用、凭据缺失、模型被停用或额度耗尽时，工作台就地说明问题出在哪、到哪里处理，而不是只报一个通用错误
- **空输入**：既没有上传文档也没有粘贴文本就点生成，界面就地提示需要需求内容
- **超长输入**：需求文档或日志远超单次可处理规模时，平台说明可处理的规模上限并给出建议（截断、分批），不静默截断
- **并发采纳**：同一批草稿被两个会话同时采纳，用例不得重复入库
- **部分失败**：批量采纳中某一条因数据问题失败，其余条目必须成功，失败条目单独回报原因
- **模型输出格式非法**：模型返回的内容无法解析时，平台说明原因并允许重试，而不是返回空结果
- **提示词注入**：需求文档或日志里含有"忽略前面的规则"之类的文字时，这些文字被当作待分析的数据，不得改变平台的行为
- **重复分析**：对同一条失败用例反复分析，历史结论各自独立留存，互不覆盖
- **无历史可依**：某条用例是首次执行时，平台明确说明缺少历史对比数据，不臆造历史规律

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 为 AI 工作台提供四个统一入口，用例生成、失败分析、日志分析、SQL 分析
- **FR-002**: 用例生成 MUST 支持从需求文档与纯文本两种输入产生用例草稿
- **FR-003**: 用例生成 MUST 支持的文档格式至少包括 PDF、Word、Markdown 与纯文本
- **FR-004**: 系统 MUST 在生成前让用户选定所属项目、采纳目标目录、测试类型与本次使用的模型
- **FR-005**: 系统 MUST 把生成的用例以草稿形态呈现，并展示标题、编码、优先级、类别、状态与步骤数
- **FR-006**: 系统 MUST 支持对草稿按状态筛选
- **FR-007**: 系统 MUST 支持对草稿批量采纳与批量驳回
- **FR-008**: 系统 MUST 只在草稿被采纳后才把用例写入正式用例库
- **FR-009**: 系统 MUST 保证同一条草稿被重复采纳不会产生重复用例
- **FR-010**: 系统 MUST 在采纳时为用例补齐前置步骤、后置步骤与断言
- **FR-011**: 系统 MUST 在草稿中标记出不合规的字段内容，且允许单条修正后继续采纳
- **FR-012**: 系统 MUST 在采纳前拦下断言取值无法获得的用例
- **FR-013**: 系统 MUST 让界面在缺少前置配置时就地说明该去哪里配置或选择，**包括但不限于**：无可用模型、项目下无目录、对象存储未配置、Web UI 用例所需元素库为空
- **FR-014**: 系统 MUST 让用户选择本次使用的模型，并在没有可用模型时就地说明如何配置
- **FR-015**: 系统 MUST 记录每次模型调用的场景、所用模型、消耗量与成败，供成本核算与效果比对
- **FR-016**: 系统 MUST 让失败分析从平台已有的执行记录中自动取得分析材料，不要求用户手工粘贴
- **FR-017**: 失败分析 MUST 覆盖请求内容、响应内容、断言失败明细、执行日志、耗时与重试次数
- **FR-018**: 失败分析 MUST 补充该用例最近若干次执行的历史，用于区分偶发与必现
- **FR-019**: 失败分析 MUST 输出按可信度排序的根因假设、每条假设的原文依据、自证清单、修复建议与复现步骤
- **FR-020**: 没有原文依据的结论 MUST 被标记为低可信
- **FR-021**: 系统 MUST 支持直接粘贴报错堆栈文本进行失败分析，输出结构与上述一致
- **FR-022**: 失败分析的复现步骤 MUST 能直接带入用例生成作为需求输入
- **FR-023**: 系统 MUST 支持从平台自身运行日志、上传日志文件、粘贴文本三种来源分析日志
- **FR-024**: 系统 MUST 把日志中的异常按特征归并为错误簇，并给出每簇的次数、首次与末次出现时间、涉及范围与样例
- **FR-025**: 系统 MUST 标记日志中错误数量异常增多的时间段
- **FR-026**: 系统 MUST 支持对任意单个错误簇发起归因，并支持一次性对排名靠前的错误簇批量归因；归因结论 MUST 引用簇内具体日志行
- **FR-027**: 系统 MUST 依据历史记录提供 SQL 慢查询排行
- **FR-028**: 系统 MUST 在分析单条 SQL 前采集其执行计划、涉及表的结构与索引信息
- **FR-029**: 系统 MUST 输出问题点、索引建议与改写后的 SQL，且结论引用上述采集结果
- **FR-030**: 系统 MUST 允许用户把改写后的 SQL 在平台内直接执行并查看结果与耗时
- **FR-031**: 系统 MUST 在采集 SQL 执行计划时保证不执行、不修改任何数据
- **FR-032**: 系统 MUST 把用户提供的文档与日志中的文本仅作为待分析数据处理，不得让其中的文字改变系统行为
- **FR-033**: 系统 MUST 对四个场景使用一致的模型选择与调用能力
- **FR-034**: 系统 MUST 在模型不可用、凭据缺失、输出无法解析等情况下给出可操作的失败原因
- **FR-035**: 系统 MUST 对 AI 产出的可执行产物（用例、改写后的 SQL）执行"先草稿后落地"流程
- **FR-036**: 系统 MUST 对分析类结论留存历史，同一对象的多次分析互不覆盖
- **FR-037**: 系统 MUST 支持把用例生成为两种类型：接口用例与 Web UI 用例
- **FR-038**: Web UI 用例的步骤 MUST 引用元素库中已沉淀的元素定位
- **FR-039**: 系统 MUST 对引用了元素库中不存在的元素的 Web UI 用例草稿标出，且要求处理后才能采纳
- **FR-040**: Appium 移动端测试类型 MUST 被预留但不在本次范围内实现
- **FR-041**: 平台自身运行日志的分析能力 MUST 按平台既有的权限模型收紧，无权限用户 MUST NOT 访问

### Key Entities

- **生成批次**：一次生成任务的汇总，归属某个项目与某个目标目录，记录任务标题、所选模型、输入来源、输入文件名、草稿数量与消耗量
- **用例草稿**：一条待审核的用例，含编码、标题、类别、优先级、审核状态、步骤数、内容、校验告警；被采纳后关联到正式用例
- **调用流水**：一次模型调用的留痕，含场景、模型、消耗量、耗时、成败与失败原因
- **分析结论**：一次分析的产出，含场景、标题、关联对象、结构化结论与所用模型
- **错误簇**：日志分析中的同类异常聚合，含特征标识、次数、首次与末次出现时间、涉及范围与样例
- **正式用例**：平台既有的用例，采纳后的用例草稿成为其中一条

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 测试人员从上传一份需求文档到看到可审核的用例草稿，全程不超过 5 分钟
- **SC-002**: 生成的用例草稿中，至少 60% 可在不改动请求内容的前提下直接采纳
- **SC-003**: 采纳后的用例在正式用例库中 100% 可被识别出其前置步骤、后置步骤与断言，不存在"断言取值取不到值却仍被采纳"的情况
- **SC-004**: 失败分析给出的根因假设中，至少 80% 带有可追溯的原文依据
- **SC-005**: 测试人员对失败用例完成"触发分析 → 得出结论"的耗时，相比人工翻阅执行日志下降 50%
- **SC-006**: 日志分析识别出的错误簇数量相比按日志行逐条处理下降一个数量级以上
- **SC-007**: 错误簇归因结论中至少 70% 被使用者判定为方向正确
- **SC-008**: 用户能对改写后的 SQL 自行执行验证，改写建议的可用率不低于 60%
- **SC-009**: 平台自身运行日志的分析能力对无权限用户不可用
- **SC-010**: 所有 AI 产出的可执行产物 100% 经由人工审核后才进入正式用例库或被执行

## Assumptions

- 目标用户是具备 API 测试基础的测试人员与开发人员，能够判断一条 AI 结论是否可信
- 平台已具备 AI 厂商与模型的管理能力，本功能复用之，不另建一套模型配置
- 平台已记录测试执行结果、SQL 执行历史与自身运行日志，本功能以这些既有数据为分析输入
- 平台已具备项目、目录、用例、前置/后置步骤、断言与元素库等既有结构，采纳后的用例沿用既有结构，不另建平行体系
- Web UI 用例的元素定位来自另一个在建的元素库功能；本功能对尚未沉淀的元素给出明确提示，不自行猜测定位
- 需求文档的解析能力由平台提供，解析失败的文档可退回纯文本输入
- 模型输出本身不可重放：同一份输入重新生成会产生不同结果。因此草稿在生成后即固定并留存，重新生成会产生新的一份草稿
- 失败分析、日志分析、SQL 分析在本次范围内只做"分析并给出结论"，不自动修复代码、不自动提交缺陷单
- 模型调用的消耗量与耗时会被记录，用于成本核算与后续按场景评测模型效果
- 平台自身运行日志包含敏感内容，其分析能力按平台既有的权限模型收紧
- 质量类成功标准（SC-002、SC-004、SC-007、SC-008）依赖人工判定，抽样规模与判定口径见 `quickstart.md` §6.1；判定结果会被记录下来供后续对比不同模型的效果
- 模块拆分、数据模型、字段规范与设计取舍见 `backend/docs/ai-workbench-design.md`（深设计附录）
