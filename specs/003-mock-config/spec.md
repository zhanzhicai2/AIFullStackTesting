# Feature Specification: Mock 配置

**Feature Branch**: `003-mock-config`

**Created**: 2026-10-30

**Status**: Draft

**Input**: User description: "Mock配置还是空的,根据现在代码情况和前端布局情况,你以软件测试架构师设计下,走specs。"

## 背景

前端路由表里已有 `/mock` 一级菜单(「Mock 配置」),当前指向"努力建设中"占位页;后端没有任何 Mock 相关表、接口或服务。本特性把这块空地做成一个**平台内置的纯静态 Mock 服务 + 规则配置台**:测试人员为被测系统配置"当收到方法+路径为 X 的请求时,返回状态码/响应头/响应体为 Y(可带延迟)"的规则;被测系统(前端联调、接口测试、压测前的数据准备)把请求直接指向平台的 mock 基地址,即可获得稳定、可控、可重复的假数据。

**决策(与用户确认)**:纯静态 Mock 服务 —— 平台只返回配置好的响应,**不转发到真实后端、不发任何外部请求**;响应体支持**请求回显变量**(把收到的请求参数回填进响应),不引入随机数,确定性优先。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 配置 Mock 规则 (Priority: P1)

测试人员在做接口联调或测试数据准备时,遇到后端接口尚未实现、不稳定、或难以造出特定数据(异常返回、超时、空列表、特定错误码)的情况。她进入「Mock 配置」页,选择所属项目,新建一条规则:选定请求方法(GET/POST/PUT/DELETE/PATCH/HEAD/OPTIONS 或任意),填写接口路径(支持 `:id` 参数占位与 `*` 通配),配置返回的 HTTP 状态码、响应头、响应体与模拟延迟,保存后启用。规则保存在项目下,随项目隔离,可随时启停、编辑、删除。

**Why this priority**: 没有规则可配,mock 服务无从谈起。规则管理是 Mock 能力的地基,也是用户每天面对的主界面。

**Independent Test**: 在一个项目下从"新建规则 → 保存 → 列表可见 → 停用再启用"完整走一遍,即可独立验证本故事交付价值。

**Acceptance Scenarios**:

1. **Given** 用户已选择一个项目, **When** 她新建一条规则并填写方法、路径与响应内容并保存, **Then** 规则出现在该项目下的规则列表中,且默认处于启用状态
2. **Given** 同一项目下已存在一条"方法 + 精确路径"相同的规则, **When** 用户再次新建相同规则, **Then** 界面就地提示已存在,不静默覆盖;用户可调整优先级或改用参数化路径
3. **Given** 规则列表已展示, **When** 用户切换规则的启用开关, **Then** 停用后该规则不再参与对外匹配,重新启用后立即恢复
4. **Given** 用户填写了超长路径、超上限的延迟或非法响应内容, **When** 她保存规则, **Then** 界面就地说明合法范围并拦截保存,不产生脏数据
5. **Given** 用户尚未选择项目, **When** 她打开 Mock 配置页, **Then** 页面就地提示先选择项目,并给出项目入口
6. **Given** 用户所选项目的应用名(`app`)为空, **When** 她查看配置页, **Then** 页面就地提示该项目的 mock 基地址不可用、需要先补全应用名
7. **Given** 所选项目下一条规则都还没有, **When** 用户查看配置页, **Then** 页面展示"如何让被测系统调用 mock 服务"的使用指引与空态引导,而不是一片空白

---

### User Story 2 - 联调时调用 Mock 服务 (Priority: P1)

被测系统(前端页面、接口测试脚本、联调的客户端)把请求指向平台的 mock 基地址 `http://{平台地址}/mock/{项目应用名}/...`,平台按"项目 → 方法 → 路径"匹配规则,返回配置好的状态码、响应头与响应体;规则配置了延迟时,按配置的毫秒数延迟返回。未命中任何规则时返回 404 业务码 JSON。整个过程平台不发任何外部请求、不执行任何代码。

**Why this priority**: 这是 Mock 功能被"调用"的一端,与 US1 共同构成完整闭环 —— US1 负责配置,US2 负责生效。缺少它,Mock 规则只是一堆无法被消费的配置。

**Independent Test**: 向 mock 基地址发起一个命中规则的请求,核对返回的状态码、响应头、响应体与延迟;再发起一个未命中的请求核对 404,即可独立验证。

**Acceptance Scenarios**:

1. **Given** 项目下存在一条命中该请求的启用规则, **When** 被测系统向 mock 基地址发起对应方法+路径的请求, **Then** 平台返回该规则配置的状态码、响应头与响应体,并按配置的延迟返回
2. **Given** 规则配置了响应体回显变量, **When** 请求携带了对应的查询参数、请求体字段或请求头, **Then** 响应体中对应位置被回填为请求携带的真实值
3. **Given** 请求未命中任何启用规则(路径不匹配、方法不匹配、或规则已停用), **When** 被测系统发起该请求, **Then** 平台返回 404 业务码 JSON,响应结构与其他平台接口一致
4. **Given** 请求路径携带的项目应用名(`app`)对应不到任何项目, **When** 被测系统发起该请求, **Then** 平台返回 404,且不泄露任何项目或规则信息
5. **Given** 两条规则都能命中同一请求(如精确路径与通配路径共存), **When** 被测系统发起该请求, **Then** 平台始终命中同一条规则(精确优先、再按优先级与创建序),两次调用结果完全一致

---

### User Story 3 - 调试与校验规则 (Priority: P2)

测试人员配置完一条规则后,希望在**交付给被测系统使用之前**先确认"这个请求会命中哪条规则、最终返回什么"。她在规则列表的调试入口填入请求方法、路径、查询参数与请求体,平台就地模拟一次匹配,展示命中规则(或提示未命中)与**变量解析后的最终响应**。

**Why this priority**: Mock 规则一旦配错,被测系统拿到的是错误的假数据,排查成本远高于配置成本。调试入口把"验证"内联到配置流程中,是规则质量的把关点;但它不阻塞核心配置链路,故排在 P2。

**Independent Test**: 对一条含回显变量的规则,用不同参数模拟请求并核对最终响应,即可独立验证。

**Acceptance Scenarios**:

1. **Given** 用户对某条规则打开调试, **When** 她填入请求方法、路径、查询参数与请求体并发起模拟, **Then** 页面展示命中该规则的匹配过程与变量解析后的最终响应
2. **Given** 用户填入的请求不会命中任何规则, **When** 她发起模拟, **Then** 页面明确提示"没有规则会命中该请求",而不是展示空响应
3. **Given** 规则响应体包含回显变量, **When** 用户保存该规则, **Then** 平台校验变量名在合法白名单内;含未知变量时拦截保存,并就地列出合法变量清单

---

### User Story 4 - 规则管理与权限 (Priority: P2)

Mock 规则是团队协作资产,由测试人员按项目沉淀、供前端联调消费。项目成员可查看本项目规则;新增、编辑、删除、启停规则等写操作限项目成员(沿用平台「项目成员表」的既有权限模型,与用例、UI 元素一致);平台超管可按既有惯例跨项目管理。

**Why this priority**: Mock 响应可能包含团队约定的假数据契约,不能允许外部人员任意篡改;同时它是协作资产,需要按项目共享可见。权限是写入通道的安全底线,随规则管理一起落地。

**Independent Test**: 用一个非项目成员账号访问该项目规则列表被拒,再用项目成员账号完成一次增删改,即可独立验证。

**Acceptance Scenarios**:

1. **Given** 用户不是该项目成员、也不是平台超管, **When** 她访问该项目的规则列表或执行任何写操作, **Then** 平台返回 403 无权限
2. **Given** 用户是项目成员, **When** 她执行新建、编辑、删除、启停任一写操作, **Then** 操作成功且结果即时反映在列表与对外服务中
3. **Given** 用户删除一条规则, **When** 她随后向 mock 基地址发起对应请求, **Then** 该请求不再被命中,返回 404
4. **Given** 用户查看规则列表, **When** 列表按方法、路径关键字、启停状态筛选并分页, **Then** 展示结果与筛选条件一致

---

### Edge Cases

- **项目应用名(app)重复**:多个项目配置了相同的 `app`,mock 基地址无法区分 —— 平台按最早创建的项目匹配,并在配置页就地提示该 app 已被占用,建议项目侧调整
- **app 为空**:项目未填 `app` 时,该项目的规则永远无法通过 mock 基地址被命中,配置页就地提示补全
- **规则路径非法**:路径含空格、控制字符或超长(> 255),保存被拦并说明范围
- **响应体非法 JSON**:用户以 JSON 模式编辑但内容非法,保存被拦并指出错误位置;用户可切换为纯文本模式存任意内容
- **延迟超上限**:延迟必须为 0~5000 毫秒的整数,超范围保存被拦
- **回显变量取不到值**:请求未携带该参数时,变量按空字符串替换,响应结构保持稳定(不报错、不抛异常)
- **精确路径与方法都相同但状态不同的规则**:通过优先级排序保证匹配确定,不出现"这次命中 A、下次命中 B"
- **对外 mock 服务无鉴权**:被测系统无法携带平台 JWT,因此 mock 基地址对知晓 `app` 的任何人开放 —— 这是设计取舍,须在使用说明中标注"不要在 mock 响应中放置真实凭据"
- **对外服务不转发、不出网**:命中规则只返回配置内容,未命中即 404,绝不把请求转发到任何真实地址 —— 从机制上排除 SSRF
- **并发编辑同一规则**:沿用平台惯例,后写入者覆盖
- **响应体为空**:允许配置"无响应体"的规则(如 204/HEAD),响应按 HTTP 语义返回空体

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 平台 MUST 提供对外 Mock 服务入口,按「项目应用名 + 请求方法 + 路径」匹配启用规则,返回规则配置的 HTTP 状态码、响应头与响应体
- **FR-002**: 用户 MUST 能在指定项目下新建、编辑、删除、查询、启停 Mock 规则;规则按项目隔离,互不可见
- **FR-003**: Mock 服务匹配结果 MUST 完全确定 —— 同一请求重复调用返回完全一致;匹配顺序按"路径精确度 → 优先级 → 创建先后"固定排序,不引入任何随机因素
- **FR-004**: 规则 MUST 支持配置响应 HTTP 状态码(默认 200)、响应头(JSON)、响应体(JSON 或纯文本)与模拟延迟(0~5000 毫秒整数,默认 0)
- **FR-005**: 响应体 MUST 支持请求回显变量:`$request.path`、`$request.query.<名>`、`$request.body.<路径>`、`$request.header.<名>`;变量集合为**封闭白名单**,未知变量在保存时被拦截,并就地列出合法变量
- **FR-006**: 请求未命中任何启用规则时,Mock 服务 MUST 返回 404 业务码 JSON(与平台其他接口响应结构一致),且不泄露项目或规则信息
- **FR-007**: 同一项目下新建规则时,若「方法 + 精确路径」已存在,MUST 就地提示冲突,不得静默覆盖
- **FR-008**: 规则路径 MUST 支持 `:id` 风格参数占位与 `*` 通配;匹配时精确路径优先于参数化路径,参数化路径优先于通配路径
- **FR-009**: 用户 MUST 能对任意规则就地发起调试:填入请求方法、路径、查询参数与请求体,展示命中规则与变量解析后的最终响应;未命中时明确提示
- **FR-010**: Mock 配置页 MUST 展示当前项目的 mock 基地址与调用示例,并支持一键复制,让被测系统可直接使用
- **FR-011**: Mock 配置页 MUST 提供就地指引:未选项目时提示选择、项目 `app` 为空时提示补全、项目下无规则时给出使用引导(对应 constitution 原则 IV 交互自成闭环)
- **FR-012**: 停用规则的 MUST 不参与对外匹配;重新启用 MUST 立即生效,无需重启任何服务
- **FR-013**: 删除规则 MUST 立即从对外匹配中移除;删除为逻辑删除,平台侧可追溯
- **FR-014**: 规则列表 MUST 支持按请求方法、路径关键字、启用状态筛选,并分页展示
- **FR-015**: Mock 规则的新增、编辑、删除、启停等写操作 MUST 按平台项目成员模型鉴权:项目成员可写,非成员 403(平台超管按既有惯例放行)
- **FR-016**: Mock 服务 MUST 只返回静态配置内容,不发起任何外部请求、不执行任何代码、不把请求转发到真实后端 —— 从机制上排除 SSRF 与任意执行面
- **FR-017**: 规则管理接口的响应结构 MUST 遵循平台 `{"code","data","msg"}` 协议与业务码约定
- **FR-018**: 项目 `app` 在项目中重复时,对外匹配 MUST 采用最早创建的项目,且在配置页 MUST 就地提示该 app 已被占用
- **FR-019**: 项目 `app` 为空时,该项目的规则 MUST 不参与对外匹配(不可达),配置页就地提示补全
- **FR-020**: Mock 基地址的路径约定 MUST 为 `/mock/{项目应用名}/...`,其中 `...` 为被测接口的原始路径;该方法与路径之外的任何内容不参与匹配

### Key Entities *(include if feature involves data)*

- **MockRule(规则)**:归属项目(project_id);请求侧:方法(GET/POST/PUT/DELETE/PATCH/HEAD/OPTIONS/ANY)、路径(支持 `:id` 占位与 `*` 通配)、路径类型(精确/参数化/通配);响应侧:HTTP 状态码、响应头(JSON)、响应体(JSON 或文本)、模拟延迟(毫秒);匹配侧:优先级、启用状态;审计侧:创建人/更新人/时间(平台通用字段)
- **项目(既有 Project)**:规则按项目隔离;`app` 字段作为 mock 基地址的项目标识,复用不改动
- **项目成员角色(既有)**:MEMBER 及以上可写,决定规则管理的写权限

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 配置一条规则到对外服务生效,用户操作路径不超过 3 步(选项目 → 新建 → 保存启用),可在一分钟内完成
- **SC-002**: 匹配 100% 确定:同一请求连续调用两次,响应逐字段完全一致(含变量解析结果);回归脚本以"两次相等"为断言
- **SC-003**: 对外 Mock 服务的响应延迟 ≤ 50ms(不含规则配置的模拟延迟),不成为被测系统的性能瓶颈
- **SC-004**: 安全面可控:新增面仅"静态响应 + 白名单回显变量",回归脚本证明 mock 服务源码中不存在任何出网调用与代码执行位
- **SC-005**: 规则质量闭环:任意含回显变量的规则,配置后可在 30 秒内通过调试入口看到"命中 + 解析后响应"的完整结果

## Assumptions

- **形态**:纯静态 Mock 服务,不做"未命中转发到真实后端",不引入 SSRF 面
- **归属维度**:规则只按项目隔离,不引入测试环境(dev/test/prod)维度 —— 环境差异由被测系统在 mock 基地址上自行区分
- **鉴权**:对外 mock 基地址无鉴权(被测系统无法携带平台 JWT),属半公开入口;规则管理接口按平台既有鉴权
- **变量范围**:MVP 仅支持请求回显变量(确定性),不支持随机数、时间戳、Jinja2 模板等任何可能破坏确定性的能力;后续扩展需重新过 constitution 原则 I
- **方法集**:支持 GET/POST/PUT/DELETE/PATCH/HEAD/OPTIONS 七种方法与 ANY;TRACE/CONNECT 不支持
- **性能**:mock 服务按平台常规规模使用,不设专门限流;不做命中统计/日志归因(MVP 范围外,后续可复用 `pity_sql_history` 的思路扩展)
- **依赖**:复用既有项目模型与项目成员权限(`Permission()` + 项目角色);不新建平行鉴权体系
